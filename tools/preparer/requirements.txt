# The Riparr Preparer.
#
# pywebview wraps the operating system's own web view -- WKWebView on macOS, WebView2 on
# Windows, WebKitGTK on Linux -- so `ui/` is hosted by the same engine the user's browser
# already uses. No Electron, nothing to download at runtime, and the interface (the part
# there is most of) did not need porting.
pywebview>=5.0

# $6$ password hashing. macOS crypt(3) has no SHA-512 support and *silently returns a DES
# hash* when asked for one, producing a card whose console login cannot work --
# discoverable only after flashing and booting. The Preparer refuses to run without this.
passlib>=1.7

# macOS only, and only for app.py, the hand-built NSWindow that predates shell.py.
# shell.py needs none of it; pywebview pulls what it needs on each platform.
pyobjc-framework-WebKit>=10.0 ; sys_platform == "darwin"

# The Wi-Fi screen, and the two frameworks it cannot work without.
#
# These were never listed, so they were never installed on the build runner and never
# collected into the bundle -- and `import CoreLocation` inside a function fails quietly.
# The effect was not an error: `location_status()` returned "unavailable", which
# `wifi_detail_status()` reports as {available: False, granted: True}, and the interface
# reads that as "this platform does not do bands" and hides both the offer *and* the
# explanation. So the packaged app showed "band unknown" against every network with no
# button to fix it and nothing on screen saying why, while a checkout with pyobjc
# installed worked perfectly. Same shape as the missing CA bundle: the frozen build is
# a different machine from the one it was built on.
#
# CoreWLAN is the scan itself -- the only source of unredacted SSIDs with bands and
# signal. CoreLocation is the permission that scan needs, and the button that asks.
pyobjc-framework-CoreWLAN>=10.0 ; sys_platform == "darwin"
pyobjc-framework-CoreLocation>=10.0 ; sys_platform == "darwin"

# CA certificates. PyInstaller bundles its own libssl and no trust store, so a frozen
# build failed every HTTPS request with CERTIFICATE_VERIFY_FAILED while the same code
# from a checkout worked -- the system Python has certificates and the bundle does not.
# core.ssl_context() names this explicitly rather than trusting what it inherits.
certifi>=2024.2.2
